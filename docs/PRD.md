## 1. 产品概述

### 1.1 一句话定位

Nook 是一个运行在 OpenWrt/ImmortalWrt 路由器上的**局域网协作小站**：设备接入同一局域网后，打开路由器上的 Nook 页面，即可在附近设备之间共享文本、发布与领取文件、或点对点直接传输文件。

### 1.2 背景与动机

跨设备传文件、同步一段文字或链接，在家庭、办公室、宿舍等局域网场景中是高频但碎片化的需求。现有方案往往依赖公网账号、云盘中转或外部服务器，存在以下问题：

- 需要登录第三方账号，引入隐私与依赖；
- 大文件经过公网云中转，速度受限、流量成本高；
- 在无公网或弱公网环境下不可用；
- 需要在每台设备上安装客户端。

Nook 把路由器本身变成一个**随时可用的本地共享空间**，用浏览器即可使用，不依赖公网账号与外部服务器，文件内容尽量在设备之间点对点传输，路由器只做轻量的信令与元信息中继。

### 1.3 价值主张

- **零客户端**：浏览器直接打开即用，无需安装 App。
- **零公网依赖**：不依赖外部服务器、云账号或公网链路。
- **本地优先**：文件内容不落路由器磁盘，尽量 P2P 直传。
- **路由器即入口**：路由器作为局域网内稳定的协作入口，开机常驻。

## 2. 目标与边界

### 2.1 目标（Goals）

- 在可信局域网内，提供文本/链接共享、文件发布与领取、点对点直接传输三类核心能力。
- 以 OpenWrt/ImmortalWrt 路由器为宿主，提供可由 init.d 管理的常驻服务。
- 提供 aarch64 与 x86_64 两种架构的 ipk / apk 安装包。
- 浏览器前端零依赖、嵌入式打包进单一二进制，便于在路由器上部署。
- 服务重启后能自动恢复可用（清空内存态、重新接受连接）。

### 2.2 非目标（Non-Goals）

- **不**提供公网或跨网传输能力，仅面向同一局域网。
- **不**提供用户账号、登录、云同步。
- **不**在路由器上持久化文件内容，文件内容只在发布者浏览器与领取者之间流转。
- **不**提供端到端加密、配对认证或访问控制（当前版本基于"可信局域网"假设）。
- **不**提供历史记录持久化，剪贴板、在线设备、文件公告均保存在内存中，服务重启即清空。
- **不**作为移动端独立产品的替代（独立移动端产品另有规划，见第 11 节）。

## 3. 目标用户与使用场景

### 3.1 目标用户

| 用户画像 | 特征 |
| --- | --- |
| 家庭用户 | 拥有一台 OpenWrt/ImmortalWrt 路由器，多台手机/电脑/平板，希望快速在设备间传文件、同步链接。 |
| 办公室成员 | 同一办公网络下，需要临时把大文件发布给同事领取，或同步一段文字/会议链接。 |
| 宿舍/小团队 | 共享同一局域网，需要一个轻量、无需账号的协作入口。 |
| 网络爱好者 | 在路由器上自行部署轻量服务，偏好标准 OpenWrt 打包、init.d 管理。 |

### 3.2 典型场景

1. **跨设备传文件**：手机拍了一张照片，想快速拿到电脑上编辑。
2. **大文件临时分发**：在办公室把一个安装包/视频临时发布给同事领取，领取完即可撤回。
3. **文字/链接同步**：把一段笔记、长链接、Wi-Fi 密码快速同步给局域网内的所有设备。
4. **临时协作入口**：家里来客，临时让大家通过路由器页面互相传文件，无需互加好友或登录。
5. **无公网环境**：断网或弱网环境下，仍可在局域网内完成设备间协作。

## 4. 术语表

| 术语 | 含义 |
| --- | --- |
| Peer | 接入 Nook 的一台设备（一个浏览器标签页即一个 Peer）。 |
| Hub | 路由器上 Nook 服务中的中心协调器，维护在线 Peer、剪贴板、文件公告元信息。 |
| 共享剪贴板（Shared Clipboard） | 局域网内所有 Peer 共享的文本/链接列表。 |
| 文件公告板（File Board） | 发布者发布的文件元信息列表，其他设备可点击领取。 |
| File Offer | 文件公告板上一条文件元信息（文件名、大小、MIME、发布者、发布时间），不包含文件内容。 |
| 直接发送（Direct Send） | 在设备列表中选定某个 Peer，直接向其发送文本或文件。 |
| WebRTC DataChannel | 浏览器之间点对点传输文件内容的通道。 |
| 信令（Signal） | 用于建立 WebRTC 连接的协商消息（offer/answer/ICE candidate），通过 Hub 中转。 |

## 5. 功能需求

> 优先级约定：P0 = 必须具备，P1 = 应具备，P2 = 可选增强。

### 5.1 设备发现与在线列表

| 项 | 内容 |
| --- | --- |
| 编号 | FR-01 |
| 优先级 | P0 |
| 描述 | 设备打开 Nook 页面后，自动接入 Hub 并出现在所有其他设备的在线列表中；离线后自动从列表移除。 |

**详细要求：**

- 设备通过 WebSocket 连接 `/ws`，连接建立后发送 `hello` 消息（携带设备名）完成注册。
- 注册成功后，Hub 向该设备发送 `welcome` 消息，包含：自身 ID、当前在线 Peer 列表、当前剪贴板内容、当前文件公告列表。
- Hub 向其他设备广播 `peer-joined`（新设备上线）与 `peer-left`（设备离线）。
- 设备断开连接时，Hub 自动注销该 Peer，并清除其发布的文件公告，广播对应的 `file-board-removed`。
- 前端在 WebSocket 断开后自动重连（3 秒间隔），并在重连后重新发送 `hello`。

**验收标准：**

- 两台设备先后打开页面，双方在线列表互相可见。
- 关闭其中一台，另一台在线列表在短时间内（受 WebSocket 读超时影响）移除该设备，且其文件公告同步消失。

### 5.2 设备命名（自定义、记忆、重置）

| 项 | 内容 |
| --- | --- |
| 编号 | FR-02 |
| 优先级 | P0 |
| 描述 | 用户可自定义设备名，可选择记忆（刷新/重连后保留），可一键重置为自动生成的默认名。 |

**详细要求：**

- 设备名最大长度 32 个字符（按 UTF-8 字符计数，见 `maxNameLen`）。
- 首次进入时，根据 `navigator.userAgent` 自动生成默认设备名（如 `iPhone-ab12`、`Windows-cd34`），后缀为随机串以避免冲突。
- 勾选 `Remember` 后，设备名存入 `localStorage`（键 `nook.deviceName` / `nook.rememberDeviceName`），刷新或重连后恢复。
- 取消勾选 `Remember` 后，清除 `localStorage` 中的设备名。
- 点击 `Reset` 恢复为自动生成的默认名，并清除记忆。
- 设备名变更通过 `hello` 消息上报 Hub。

**验收标准：**

- 修改设备名后，其他设备在线列表显示新名称。
- 勾选 Remember 并刷新页面，名称保留；取消勾选并刷新，恢复默认名。

### 5.3 共享剪贴板

| 项 | 内容 |
| --- | --- |
| 编号 | FR-03 |
| 优先级 | P0 |
| 描述 | 局域网内所有设备共享一个文本/链接列表，任何设备可发布，所有设备实时同步。 |

**详细要求：**

- 发布：用户在输入框粘贴/输入文本，点击 `Post` 或使用 `Ctrl/Cmd + Enter` 提交，发送 `clipboard-add`。
- 限制：单条文本最大 64 KB（`maxClipboardTextBytes`）；列表最多保留 50 条（`maxClipboardItems`），超出时丢弃最旧的一条（新条目前插）。
- 同步：Hub 接收后向所有 Peer 广播 `clipboard-added`。
- 初始同步：新设备 `welcome` 时携带当前完整剪贴板列表。
- 展示：每条显示发布者名、发布时间、文本内容；URL 自动转为可点击链接。
- 操作：每条提供 `Copy`（复制到系统剪贴板，带降级方案）；提供 `Paste` 按钮读取系统剪贴板到输入框。
- 每条剪贴板包含字段：`id`、`from`（发布者 ID）、`fromName`、`text`、`createdAt`（毫秒时间戳）。

**验收标准：**

- 一台设备发布文本，所有设备列表实时出现该条目。
- 发布超过 50 条后，列表保持 50 条，最旧的被丢弃。
- 发布 64 KB 文本成功；超过 64 KB 的文本被拒绝（不写入、不广播）。
- 服务重启后剪贴板为空。

### 5.4 文件公告板

| 项 | 内容 |
| --- | --- |
| 编号 | FR-04 |
| 优先级 | P0 |
| 描述 | 设备可发布一个或多个本地文件的元信息到公告板，其他设备可点击领取，发布者可撤回或清空自己的公告。 |

**详细要求：**

- 发布：选择一个或多个文件，前端为每个文件生成 `id` 并暂存文件对象，发送 `file-board-add`（携带文件名、大小、MIME）。
- 元信息：Hub 仅保存 `FileOffer` 元信息（`id`、`from`、`fromName`、`name`、`size`、`mime`、`createdAt`），**不保存文件内容**。
- 限制：公告板最多 100 条（`maxFileOffers`），超出时移除最旧的一条。
- 同步：Hub 接收后广播 `file-board-added`；新设备 `welcome` 时携带当前完整公告板。
- 领取：其他设备点击 `Receive`，发送 `file-board-request`；Hub 将请求转发给发布者；发布者通过 WebRTC DataChannel 向请求者发起文件传输（见 5.6）。
- 撤回：发布者可对自己的公告点击 `Remove`（单条撤回），发送 `file-board-remove`；Hub 删除并广播 `file-board-removed`。
- 清空：发布者可点击 `Clear Mine` 清空自己发布的所有公告。
- 失效：发布者断开连接时，其所有公告自动失效并被广播移除；领取时若发布者已离线或为自己，返回 `file-board-unavailable`。
- 展示：按发布时间倒序，显示文件名、发布者、大小、时间；自己的公告显示 `Remove`，他人公告显示 `Receive`，并带状态文字（如 `Requesting...`、`Sending...`、`Downloaded`、`Unavailable`）。

**验收标准：**

- 发布文件后，所有设备公告板实时出现该条目（仅元信息，不含内容）。
- 发布者关闭页面后，其公告从所有设备消失。
- 发布者点击 `Clear Mine`，自己发布的所有公告被移除并同步。
- 领取已下线的发布者的文件，显示 `Unavailable`。

### 5.5 直接发送（文本 / 文件）

| 项 | 内容 |
| --- | --- |
| 编号 | FR-05 |
| 优先级 | P0 |
| 描述 | 用户可在设备列表中点击某个在线设备，直接向其发送文本或文件。 |

**详细要求：**

- 入口：设备列表中点击任一在线设备，弹出 `Send to <name>` 模态框。
- 直接文本：输入文本后点击 `Send Text`，通过 WebRTC DataChannel 发送 `{type:"text"}`。
- 直接文件：选择文件后，通过 WebRTC DataChannel 发起文件传输（见 5.6）。
- 接收方：弹出 `Incoming from <name>` 模态框，对文件提供 `Accept` / `Reject`；文本可直接查看并 `Copy`。
- 直接发送不经过 Hub 存储内容，Hub 仅中转 WebRTC 信令。

**验收标准：**

- A 设备向 B 设备直接发送文本，B 收到弹窗并显示内容。
- A 向 B 直接发送文件，B 接受后收到完整文件并可下载；B 拒绝则 A 侧状态显示 `Rejected`。

### 5.6 文件传输（WebRTC DataChannel）

| 项 | 内容 |
| --- | --- |
| 编号 | FR-06 |
| 优先级 | P0 |
| 描述 | 文件内容通过浏览器间 WebRTC DataChannel 点对点传输，Hub 仅做信令中转，默认不使用 ICE 服务器。 |

**详细要求：**

- 信令：通过 WebSocket `signal` 消息中转 `offer` / `answer` / `candidate`；Hub 按 `to` 字段定向转发给目标 Peer，并附上 `from`。
- ICE 配置：默认 `iceServers: []`（局域网内直接连接，无需 STUN/TURN），由 `/config` 接口下发。
- 数据通道：按需创建 `filetransfer` 通道；分块大小 64 KB（`CHUNK_SIZE`）。
- 文件传输协议（DataChannel 内 JSON 控制消息 + 二进制分块）：
  - 发送方先发 `{type:"file-offer", id, boardId?, name, size, mime}`。
  - 接收方回 `{type:"file-accept"}` 或 `{type:"file-reject"}`。
  - 发送方收到 accept 后按 64 KB 分块流式发送二进制数据。
  - 发送完成后发 `{type:"file-done", id}`。
  - 接收方组装 Blob 并触发浏览器下载。
- 传输状态机：`waiting → accepted → sending → done`，或 `rejected` / `error`。
- 进度：传输列表显示进度条与状态徽标（`Waiting` / `Sending...` / `Receiving...` / `Sent` / `Downloaded` / `Rejected`）。
- 文件公告领取与直接发送共用同一套传输机制；公告领取时携带 `boardId` 以便更新公告状态。

**验收标准：**

- 在同一局域网内，A 向 B 直接发送一个数 MB 文件，B 接受后下载到的文件与源文件大小一致。
- 公告板领取场景下，发布者页面保持打开，领取者能完整下载文件。
- 发布者刷新页面后，相关公告失效，领取者无法继续领取。

### 5.7 传输管理

| 项 | 内容 |
| --- | --- |
| 编号 | FR-07 |
| 优先级 | P1 |
| 描述 | 页面提供"最近直接传输"列表，展示进行中与已完成的传输及其状态。 |

**详细要求：**

- 列表展示每个传输的文件名、大小、进度条、状态徽标。
- 新传输前置入列表。
- 状态包括：`waiting` / `sending` / `receiving` / `done` / `rejected` / `error`。

**验收标准：**

- 发起或接收一个直接文件传输后，列表出现对应条目并随传输进度更新。

### 5.8 系统配置与版本信息

| 项 | 内容 |
| --- | --- |
| 编号 | FR-08 |
| 优先级 | P0 |
| 描述 | 页面显示当前服务版本号；服务监听地址可通过 OpenWrt 配置文件或命令行参数调整。 |

**详细要求：**

- 前端启动时请求 `/config`，获取 `version` 与 `rtc.iceServers`，并在页头显示版本徽标（`dev` 或 `v0.x.x`）。
- `/config` 返回 JSON：`{"version":"<version>","rtc":{"iceServers":[]}}`。
- 版本号来自构建期注入的 `version` 变量（默认 `dev`）。
- 服务监听地址默认 `0.0.0.0:8088`，可通过 `-listen` 参数覆盖。
- OpenWrt 配置文件 `/etc/config/nook` 提供 `enabled` 与 `listen` 选项，由 init.d 脚本读取并传给二进制。

**验收标准：**

- 页面版本徽标与实际构建版本一致。
- 修改 `/etc/config/nook` 的 `listen` 并 `/etc/init.d/nook restart` 后，服务在新地址监听。

### 5.9 连接与会话管理

| 项 | 内容 |
| --- | --- |
| 编号 | FR-09 |
| 优先级 | P0 |
| 描述 | 服务通过 WebSocket 维持与每个设备的双向会话，具备心跳、读超时与来源校验。 |

**详细要求：**

- WebSocket 升级时校验 `Origin`：无 Origin 放行；有 Origin 时要求其 Host 与请求 Host 一致（防跨站 WebSocket 劫持）。
- 读限制：单条消息最大 65536 字节。
- 心跳：服务端每 30 秒发送 Ping；客户端回 Pong 后将读截止时间续期 60 秒。
- 写超时：单次写操作 10 秒超时。
- 优雅关闭：收到 SIGINT/SIGTERM 后，服务在 5 秒超时内优雅关闭。
- 发送缓冲：每个 Peer 拥有 32 容量的发送通道；满时丢弃以避免阻塞。

**验收标准：**

- 跨站页面无法建立 WebSocket 连接（Origin 校验生效）。
- 长时间空闲连接因心跳维持而不被断开；网络中断后连接在 60 秒内被检测并清理。

## 6. 非功能需求

### 6.1 性能

- 单个 WebSocket 消息最大 64 KB（读限制 65536 字节），超出会被拒绝读取。
- 剪贴板单条上限 64 KB，列表上限 50 条。
- 文件公告板上限 100 条。
- 文件分块 64 KB，文件大小本身无服务端硬限制（受浏览器与设备性能约束）。
- 路由器侧不传输文件内容，CPU/内存/带宽开销主要来自 WebSocket 信令与元信息存储，适合在低端路由器上运行。

### 6.2 可靠性

- 服务在 OpenWrt 上通过 procd 管理，配置 `respawn`，异常退出后自动重启。
- 内存态在服务重启后清空，属于已接受的 设计取舍（非数据丢失缺陷）。
- WebSocket 断开后前端自动重连（3 秒间隔），重连后重新注册并拉取最新状态。

### 6.3 安全

- **威胁模型**：当前版本面向可信局域网，不提供认证、加密或访问控制。任何能访问路由器 8088 端口的局域网设备均可使用 Nook。
- WebSocket Origin 校验，防止跨站劫持。
- 设备 ID 使用 UUID 前 8 位，避免可预测。
- 文件内容不落路由器磁盘，降低路由器存储与泄露风险。
- **已知限制（非本版本范围）**：
  - 无端到端加密，局域网内流量可被嗅探（WebRTC DataChannel 在无 ICE/无 TURN 的纯局域网场景下为明文/SCTP）。
  - 无设备配对或访问控制，恶意局域网设备可发布/领取文件。
  - 上述限制在可信局域网假设下可接受，加密与配对规划在后续版本。

### 6.4 兼容性

- 服务端：Go 标准库 + `gorilla/websocket` + `google/uuid`，依赖极简，支持交叉编译至 linux/arm64 与 linux/amd64。
- 前端：纯 HTML/CSS/JS，零第三方依赖；需浏览器支持 WebSocket 与 WebRTC DataChannel。
- 打包：aarch64_generic 与 x86_64 两种架构，各提供 ipk（opkg）与 apk（apk 包管理器）格式。
- 宿主：OpenWrt / ImmortalWrt，遵循标准 init.d 与 `/etc/config` 约定。

### 6.5 可维护性

- 前端嵌入二进制（`embed.FS`），部署为单一可执行文件 + init.d 脚本 + 配置文件。
- 版本号在构建期注入，页面与日志可观测。
- 代码遵循简洁标准库优先的风格，避免不必要的注释与依赖（见 `AGENTS.md`）。

## 7. 技术架构与数据流

### 7.1 组件概览

```
┌──────────────────────────────────────────────────────────────┐
│  路由器 (OpenWrt/ImmortalWrt)                                 │
│                                                               │
│   /usr/bin/nook  ──  /etc/init.d/nook  ──  /etc/config/nook   │
│        │                                                      │
│        ▼                                                      │
│   ┌─────────────────────────────────────────┐                 │
│   │ Nook 进程 (Go)                          │                 │
│   │  - HTTP 路由: /  /ws  /config           │                 │
│   │  - Hub (内存态: peers/clipboards/offers)│                 │
│   │  - embed.FS 前端 (web/*)                │                 │
│   └─────────────────────────────────────────┘                 │
│        │              │              │                        │
└────────┼──────────────┼──────────────┼────────────────────────┘
         │ WebSocket    │ /config      │ HTTP (静态资源)
         │ (信令/元信息) │              │
         ▼              ▼              ▼
   ┌──────────┐    ┌──────────┐   ┌──────────┐
   │ 设备 A    │    │ 设备 B    │   │ 设备 C    │
   │ 浏览器    │◄──►│ 浏览器    │   │ 浏览器    │
   │          │ WebRTC DataChannel │          │
   └──────────┘    └──────────┘   └──────────┘
        ▲               ▲              ▲
        └───────────────┴──────────────┘
            文件内容 P2P 直传（不经过路由器）
```

### 7.2 关键路径

1. **设备接入**：浏览器加载 `/` → 请求 `/config` → 建立 `/ws` → 发送 `hello` → 收到 `welcome`（含在线设备、剪贴板、文件公告）。
2. **剪贴板发布**：浏览器发 `clipboard-add` → Hub 写入内存并广播 `clipboard-added` → 所有设备更新列表。
3. **文件公告**：浏览器发 `file-board-add`（仅元信息） → Hub 写入内存并广播 `file-board-added`。
4. **文件领取**：领取者发 `file-board-request` → Hub 转发给发布者 → 发布者经 WebRTC DataChannel 直接向领取者传文件内容（`file-offer` → `file-accept` → 分块 → `file-done`）。
5. **直接发送**：发送者与目标 Peer 通过 `signal` 协商 WebRTC → 建立 DataChannel → 传文本或文件。
6. **设备离线**：WebSocket 断开 → Hub 注销 Peer → 广播 `peer-left` → 清理该 Peer 的文件公告并广播 `file-board-removed`。

### 7.3 协议（WebSocket 消息）

消息为 JSON，顶层字段见 `Message` 结构。主要 `type`：

| type | 方向 | 说明 |
| --- | --- | --- |
| `hello` | C→S | 上报设备名，完成注册 |
| `welcome` | S→C | 注册成功，下发自身 ID / 在线设备 / 剪贴板 / 文件公告 |
| `peer-joined` | S→C | 广播：新设备上线 |
| `peer-left` | S→C | 广播：设备离线 |
| `signal` | C→S / S→C | WebRTC 信令中转（offer/answer/candidate），按 `to` 定向 |
| `clipboard-add` | C→S | 发布剪贴板 |
| `clipboard-added` | S→C | 广播：新剪贴板条目 |
| `file-board-add` | C→S | 发布文件公告（仅元信息） |
| `file-board-added` | S→C | 广播：新文件公告 |
| `file-board-remove` | C→S | 撤回自己的文件公告 |
| `file-board-removed` | S→C | 广播：文件公告已移除 |
| `file-board-request` | C→S / S→C | 领取请求（C→S） / 转发给发布者（S→C） |
| `file-board-unavailable` | S→C | 领取失败（发布者离线或为自己） |
| `error` | S→C | 错误（如目标 Peer 不存在） |

### 7.4 资源与限制常量

| 常量 | 值 | 位置 |
| --- | --- | --- |
| 默认监听地址 | `0.0.0.0:8088` | `main.go` / `nook.config` |
| 设备名最大长度 | 32 字符（UTF-8） | `hub.go` `maxNameLen` |
| 剪贴板单条最大 | 64 KB | `hub.go` `maxClipboardTextBytes` |

## 8. 部署与发布

### 8.1 部署形态

- 二进制：`/usr/bin/nook`
- 服务脚本：`/etc/init.d/nook`（procd 管理，`respawn` 自动重启，`START=95`）
- 配置文件：`/etc/config/nook`（`enabled`、`listen`）

### 8.2 安装与升级行为

- 首次安装后**不自动启动**服务。
- 升级时若 `nook` 服务正在运行，安装完成后**自动重启**服务。
- 升级前若服务未运行，安装完成后**不自动启动**。

### 8.3 发布物

以 `v` 开头的 Git tag 触发 CI（`.github/workflows/build.yml`）构建并发布：

```
nook_<version>-1_aarch64_generic.ipk
nook_<version>-1_x86_64.ipk
nook_<version>-r1_aarch64_generic.apk
nook_<version>-r1_x86_64.apk
```

安装示例：

```sh
# opkg
opkg install ./nook_<version>-1_aarch64_generic.ipk

# apk（未签名本地包需允许不受信任）
apk add --allow-untrusted ./nook_<version>-r1_aarch64_generic.apk
```

### 8.4 服务管理

```sh
/etc/init.d/nook enable     # 开机自启
/etc/init.d/nook start      # 启动
/etc/init.d/nook stop       # 停止
/etc/init.d/nook restart    # 重启
```

## 10. 风险与已知限制

| 风险/限制 | 说明 | 缓解/后续 |
| --- | --- | --- |
| 可信局域网假设 | 无认证/加密，恶意局域网设备可滥用 | 文档说明使用前提；后续版本评估配对/TLS |
| 内存态易失 | 重启后剪贴板/公告清空 | 已接受；如需持久化另行评估 |
| 发布者须在线 | 文件内容存于发布者浏览器，关闭即失效 | UI 提示；属设计取舍 |
| WebRTC 兼容性 | 依赖浏览器 WebRTC 支持 | 文档声明浏览器要求 |
| P2P 建连失败 | 同子网但防火墙/浏览器策略导致无法直连 | 提示检查网络与浏览器；暂不提供 TURN |
| 路由器资源 | 低端路由器 CPU/内存有限 | 设计上路由器不承载文件内容，开销可控 |
